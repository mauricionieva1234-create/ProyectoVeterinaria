1. Introducción

Este proyecto consiste en una aplicación web para la gestión diaria de una clínica veterinaria pequeña. El sistema permite registrar el ingreso de los pacientes, organizar la cola de espera y las urgencias, acompañar la visita clínica, conservar la historia completa, administrar controles y avisos, cobrar las visitas y emitir el cierre de caja del día.

La idea fue resolver un problema concreto y reconocible: en una veterinaria, la información suele estar repartida entre planillas, papeles y la memoria del personal. Eso dificulta saber quién falta atender, qué pasó en una visita anterior, cuánto se debe o cuánto se recaudó. Un sistema único, con reglas claras y permisos por rol, ordena ese flujo y evita perder información.

El desarrollo se organizó en etapas, cada una cerrada con sus pruebas y su documentación:

  1. Base y seguridad: monorepo, endpoint de salud, migraciones, seeds, inicio de sesión con cookie, permisos por rol, auditoría y administración de usuarios.
  2. Catálogos y fichas: especies, razas, franjas horarias, clientes y pacientes, con búsqueda previa para evitar duplicados.
  3. Recepción: cola diaria, urgencias, alta rápida, controles y avisos.
  4. Clínica: visitas con versiones, medicación, registros, adjuntos, historia clínica imprimible y asistente local de consultas.
  5. Cobros y caja: cobro por visita, pagos por medio, deudas, anulaciones auditadas y cierre diario calculado.
  6. Lista de precios y detalle: precios con historial, ítems con snapshot, total calculado y detalle visible desde la caja.
  7. Endurecimiento: accesibilidad de modales, carga por rutas, backups verificables y prueba del flujo completo.

El resultado es un sistema demostrable de principio a fin, con una arquitectura explicable y un código preparado para seguir creciendo.

2. ¿Por qué elegimos este proyecto?

Elegimos una veterinaria porque es un dominio cotidiano, fácil de entender y con suficientes reglas de negocio para poner en práctica casi todo lo visto en la materia. No hace falta explicar qué es una urgencia o un control, pero sí decidir cómo se modelan: quién puede confirmarla, qué pasa si se reprograma, cómo se conserva lo que se escribió en una visita.

Razones principales

  • Problema real y cercano. Permite mostrar una aplicación útil, no un ejercicio aislado: alta de fichas, cola, atención, cobro y caja forman un flujo completo.
  • Reglas de negocio ricas. Cerrar una visita exige motivo; cada edición genera una versión; nada clínico se borra, se anula; el cierre del día se calcula, no se guarda. Son reglas que obligan a pensar el modelo y no solo la interfaz.
  • Cobertura del temario.modelado relacional, SQL, API REST, arquitectura en capas, patrones, validaciones, autenticación, pruebas y control de versiones aparecen de forma natural.
  • Crecimiento por módulos. Cada etapa agregó funcionalidad sin reescribir lo anterior, gracias a la separación entre rutas, servicios y repositorios.
  • Trabajo con datos sensibles. El proyecto usa exclusivamente datos ficticios, enmascara documentos en los listados y no registra información personal en logs.
Decisión de alcance: se dejaron fuera la venta de productos, el control de stock y la facturación fiscal. Incluirlos habría desviado el esfuerzo del objetivo principal: ordenar la atención clínica y el cobro de las visitas.

En síntesis: es un proyecto lo bastante simple para ser demostrado en clase y lo bastante completo para justificar decisiones de arquitectura, diseño y calidad.

4. Arquitecturas de software

La solución sigue una arquitectura cliente-servidor: un navegador consume una API REST sobre HTTP. El backend es un monolito modular organizado en capas, y el frontend está dividido por responsabilidades. No se usaron microservicios ni arquitectura hexagonal pura: para el tamaño del proyecto y del equipo, esa complejidad no aportaba beneficios.

Capas del backend

CapaResponsabilidad
RutasDefinen los endpoints, aplican autenticación, permisos y validación, y delegan en el controlador.
ControladorTraduce la petición HTTP en una llamada al servicio y devuelve la respuesta con el código adecuado.
ServicioContiene las reglas de negocio: estados, totales, motivos obligatorios, anulaciones y auditoría.
RepositorioConcentra el SQL parametrizado. No decide reglas, solo persiste y consulta.
Base de datosGarantiza integridad con claves foráneas, restricciones, índices y transacciones.

La cadena de middleware se declara de forma explícita en cada módulo, de modo que una petición pase por autenticación, permiso y validación antes de llegar al controlador:

backend/src/modulos/precios/rutas.js
rutasPrecios.use(requiereAutenticacion);

rutasPrecios.get(
  '/',
  requierePermiso('precios.ver'),
  validarConsulta(esquemaListadoPrecios),
  controlador.listar,
);

rutasPrecios.patch(
  '/:id',
  requierePermiso('precios.editar'),
  validar(esquemaActualizarPrecio),
  controlador.actualizar,
);

En el frontend, las páginas se cargan de forma diferida (lazy loading) y están protegidas por guardas: RutaProtegida exige sesión, RutaPermiso exige un permiso concreto y RutaAdmin restringe las funciones de administración. El cliente HTTP es único y centraliza errores y credenciales.

Decisión importante: el backend es la única autoridad en materia de permisos. Que el frontend oculte un botón es una comodidad visual; si un usuario llama a la API sin permiso, el middleware responde 403.

Repository y SQL parametrizado

backend/src/modulos/precios/repositorio.js
export async function buscarPrecioPorId(id, cliente, { bloquear = false } = {}) {
  const { rows } = await ejecutar(
    `SELECT ${CAMPOS_PRECIO}
     FROM precio p
     WHERE p.id = $1
     ${bloquear ? 'FOR UPDATE OF p' : ''}`,
    [id],
    cliente,
  );
  return rows[0] ?? null;
}

El valor viaja como parámetro $1, nunca concatenado. El parámetro cliente permite reutilizar la misma conexión dentro de una transacción.

Servicio: reglas de negocio

backend/src/modulos/cobros/servicio.js
// El subtotal se redondea por línea y el total suma esos subtotales. Así el
// total del cobro coincide siempre con lo que muestra el detalle en la base.
function totalDeItems(items) {
  const subtotales = items.map((item) => redondear(item.cantidad * item.importeUnitario));
  return redondear(subtotales.reduce((suma, valor) => suma + valor, 0));
}

const items = datos.items !== undefined ? normalizarItems(datos.items) : null;
const total = items ? totalDeItems(items) : redondear(datos.total);
const estado = total === 0 ? 'pagado' : 'pendiente';

Acá se decide qué significa «cobrar»: con ítems el total se calcula, sin ítems se respeta el total manual, y un total cero con observación queda marcado como pagado. La ruta no sabe nada de esto.

Transacciones

backend/src/utils/transaccion.js
export async function conTransaccion(funcion) {
  const cliente = await obtenerPool().connect();
  try {
    await cliente.query('BEGIN');
    const resultado = await funcion(cliente);
    await cliente.query('COMMIT');
    return resultado;
  } catch (error) {
    await cliente.query('ROLLBACK');
    throw error;
  } finally {
    cliente.release();
  }
}

Es una forma simple de aplicar el principio ACID: si falla la auditoría después de crear un cobro, se revierte también el cobro.

Validación con esquemas

backend/src/modulos/precios/esquemas.js
// Toda edición exige motivo. Si cambia el nombre o el importe, además deja una
// fila en el historial.
export const esquemaActualizarPrecio = z
  .object({
    nombre: nombre.optional(),
    importe: importe.optional(),
    activo: z.boolean().optional(),
    observaciones: textoOpcional(1000, 'Las observaciones son demasiado largas'),
    motivo,
  })
  .refine(
    (datos) => datos.nombre !== undefined || datos.importe !== undefined ||
                datos.activo !== undefined || datos.observaciones !== undefined,
    { message: 'No hay cambios para guardar' },
  );

Control de acceso en la interfaz

frontend/src/componentes/RutaPermiso.jsx
export function RutaPermiso({ permiso, children }) {
  const { data, isPending } = useSesion();
  if (isPending) return <p role="status">Cargando sesión...</p>;
  if (!(data?.permisos ?? []).includes(permiso)) {
    return <Navigate to="/no-autorizado" replace />;
  }
  return children;
}

Otras prácticas adoptadas

  • Convenciones uniformes: dominio en español, tablas en snake_case y términos técnicos estándar en inglés.
  • Commits chicos y frecuentes, en español, con prefijos feat:, fix:, test:, docs: y chore:.
  • Un plan escrito antes de cada etapa y una documentación del modelo de datos como fuente de verdad.
  • Formato de fecha y hora en español de Argentina, zona horaria de Tucumán.
  • Accesibilidad mínima: modales con foco atrapado, cierre con Escape y nombre accesible.
  • Datos de prueba siempre ficticios, nunca reales.

7. Conclusión de la materia

Metodología de Sistemas II permitió pasar de la idea de una aplicación a un sistema completo y justificable. El aprendizaje más importante no fue solo escribir código, sino tomar decisiones y saber explicarlas: por qué separar un servicio de un repositorio, por qué no borrar una visita, por qué calcular el total desde los ítems y por qué el permiso se comprueba en el servidor aunque el botón esté oculto.

Durante el desarrollo aparecieron situaciones que el temario ayuda a resolver: un cambio en la lista de precios no podía alterar cobros antiguos (se resolvió con un snapshot por ítem); una edición de precios debía conservar el motivo y el valor anterior (historial append-only); un cobro con pagos parciales no podía reducirse por debajo de lo ya pagado (regla en el servicio y transacción para mantener la coherencia). Cada una de esas decisiones quedó documentada y probada.

También quedó claro que la arquitectura no es un dibujo: es una herramienta para trabajar. Gracias a la separación en módulos y capas, cada etapa se pudo agregar sin desarmar las anteriores, y las pruebas dieron confianza para seguir avanzando. El uso de estándares —SQL parametrizado, API REST, cookies httpOnly, migraciones, formato consistente— evitó soluciones improvisadas.

Como resultado se obtiene una aplicación veterinaria con historial clínico, cobros, caja y lista de precios, con un repositorio ordenado y documentación suficiente para que otra persona pueda entenderla y continuarla. Los próximos pasos naturales serían la venta de productos con stock y reportes, siempre preservando las reglas y la arquitectura ya construidas.

Cierre: el proyecto cumple el objetivo planteado: resolver un problema concreto aplicando los conceptos de la materia de manera demostrable, mantenible y verificable.
